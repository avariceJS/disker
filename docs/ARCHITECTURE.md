# Architecture

## Modules

- `DiskerCore` contains storage measurements, selected-folder scanning, bounded history, and bounded selected-scope bookmarks.
- `DiskerApp` is a native SwiftUI macOS application with an `NSOpenPanel` for user-selected scan scope and Finder reveal.
- `DiskerCoreChecks` is a small executable check suite using temporary synthetic trees and a synthetic `.app` Info.plist; run it with `scripts/check-core.sh`.

## Measurement contract

Volume total and available capacity are separate system-provided values. Disker prefers macOS's important-usage availability estimate when it is positive; if it is zero/unavailable, it falls back to the standard volume available-capacity value and labels that basis. Disker derives `notAvailableBytes = total - available`; it does not call this physical file usage because reservations and APFS/macOS accounting are not attributable to a path scan.

The Overview shows a low-availability review signal when available capacity falls below the larger of 10 GiB or 5% of the reported total. This threshold is a dashboard heuristic, not an alert, usage attribution, or estimate of reclaimable space.

Folder scans open selected directories and descend with descriptor-relative `openat` and `fstatat`, always using `O_NOFOLLOW`/`AT_SYMLINK_NOFOLLOW` for descendants. This avoids following a child directory replaced by a symlink during a scan. Disker verifies that an opened directory still has the device/inode identity seen during enumeration, compares directory link count, modification time, and change time before and after listing, and rechecks regular-entry identity, type, size, allocated blocks, modification time, and change time after enumerating each parent. If that evidence changes, the affected subtree and root are marked partial with a separate changed-during-scan count. This catches many directory-entry and in-place file mutation races, but cannot freeze the tree or detect every change after an entry's final recheck. Symlinks are not traversed; a selected symlink root is reported as incomplete. Only regular files contribute to file size and filename-extension totals. Sockets, FIFOs, device nodes, and other special filesystem entries are excluded and separately reported as incomplete coverage for their containing subtree and selected root. Each regular `(device, inode)` is counted once per selected root. Logical bytes are `st_size`; allocated bytes are `st_blocks * 512`. These estimates can diverge from reclaimable space because clones and shared blocks are not attributed. A failed metadata lookup or directory access marks that root incomplete.

Scan progress reports the latest path after every 256 traversed directory entries and whenever 256 additional unique regular-file objects have been counted. The displayed file-object count deduplicates hard links; entry-based updates ensure a large tree of empty directories still reports progress.

Each folder scan records the selected path, observation time, logical and allocated estimates, file count, inaccessible count, excluded symlink count, and completion state. It stores at most the 100 largest descendant-directory summaries and, independently, the 20 largest nested directories with a direct regular `.git` entry. These are overlapping subtree totals and are explicitly presented as non-additive. A direct `.git` directory is additionally retained as a selected-root-relative measurement even when it falls outside that ranking; a direct `.git` file remains only a marker, and symlinks and special entries are not repository markers. The UI labels nested paths as repository-marker candidates without claiming verified project ownership. Their history is compared only for the same selected root and exact relative path across complete observations. Git metadata comparisons require the same selected root and `.git` relative path plus complete observations. A directory's coverage is incomplete when an inaccessible item or excluded symlink lies within its subtree. Hard-linked bytes are assigned to the UTF-8 lexicographically first relative file path, making sibling directory attribution deterministic.

Folder observations retain at most 30 filename-extension aggregates, ordered by allocated-byte estimate. The Overview shows the five largest retained categories. Extension parsing uses only the last filename component, lowercases safe ASCII extensions up to 32 bytes, and groups extensionless, unusual, or longer values into bounded labels. It never reads content or verifies file type or purpose. A hard-linked file object is assigned the extension of its deterministic retained path. When more than 30 categories occur, the observation retains their combined logical bytes, allocated-byte estimate, and file count in a separate “other extensions” aggregate, so the bounded category detail still reconciles to the measured file totals. The UI shows this remainder and how many categories it combines. The remainder is not treated as a stable extension for history comparisons. For the latest complete scan of an exact selected root, Disker can show positive category-level allocated-estimate deltas against its previous complete scan. It suppresses that comparison if either scan is partial, a newer partial scan exists, old history lacks categories, or either category list was truncated. Extension categories are metadata summaries, not cleanup or safety signals.

The native folder picker and scan entry point cap each observation at 50 selected roots, matching the existing maximum app-folder association count. Over-limit selections are rejected before bookmark creation or scanning so one observation cannot grow without bound from an accidental bulk selection.

The overview's folder-growth highlights are the largest three positive allocated-byte deltas for each path's latest complete scan against its previous complete scan. Paths are never compared across roots. A newer partial scan suppresses that path's older signal, and shrinking or unchanged paths are omitted. These highlights are historical selected-path evidence, not a claim that a folder caused a system-capacity change.

The overview separately highlights up to three growing descendant paths. A directory is compared only with the same relative path under the same selected root and the previous complete observation. The path must appear in both retained summaries; an omitted path is not interpreted as zero even when a top-directory summary was truncated. A newer partial root scan suppresses older signals. These are allocated-byte estimates and do not establish project ownership.

To keep the Overview concise, it shows only the three largest roots with summary metrics. The Folders page remains the place for per-root histories, filename categories, Git metadata, and retained descendant details.

For project context, Disker flags a selected directory when it contains a direct, non-symlink `.git` entry. A direct `.git` directory's file-tree metrics are surfaced as “Git metadata in this selected folder”; this narrow measurement is not project ownership or reclaimable-space attribution. Disker does not read a `.git` file, claim project ownership, or infer that the repository's contents are disposable. Nested repository markers are attached only to their immediate containing directory.

The Applications view offers an `NSOpenPanel` restricted to application bundles and measures only the explicitly chosen `.app` tree. During this explicit app-selection flow, Foundation reads the selected bundle's declared `CFBundleIdentifier` from its `Info.plist`; Security reads the embedded App Groups claims and [`SecStaticCodeCheckValidity`](https://developer.apple.com/documentation/security/code-signing-services) performs strict local signature validation. This may read signed executable and resource contents locally, runs off the main thread, and never uploads them. It verifies local code integrity, not Gatekeeper/notarization trust or publisher identity. The generic folder-size scanner still reads filesystem metadata only. The declared ID, embedded group claims, signature-validation result, and signed identifier are stored with that bundle's observation. To keep local history bounded against pathological bundle metadata, Disker ignores a claim list with more than 256 entries or 64 valid unique group IDs, and ignores IDs longer than 255 bytes. When the user later associates an exact folder path, a matching signed identifier receives a stronger match label for the selected user's `~/Library/Containers/<bundle-id>` directory or a descendant; a matching ID from an unvalidated signature remains probable. A path under `~/Library/Group Containers/<group-id>` receives a signature-covered shared-claim label only when the signature validates, its signed identifier matches the declared ID, and its embedded entitlement lists that exact group ID. This is a more specific claim label, not proof of developer trust or OS-granted access. Otherwise, a matching embedded claim is labeled declared and unvalidated. App-group data is shared; neither label implies current use or exclusive ownership. All other links remain labeled user-selected and unverified. History indexes only selected roots whose path has an `.app` extension. The user can separately choose folders and associate them with that exact bundle path; Disker stores up to 180 associations with at most 50 paths per app and rejects an over-limit addition without dropping prior links. Each path's measurements are shown separately, never summed, because paths may overlap or be shared. Removing a relationship changes only Disker's local metadata; clearing history also clears the associations. Bundle contents can include excluded symlinks, which leave the estimate partial. Unselected support folders, caches, containers, and shared dependencies are not discovered; there is no uninstall operation or consequence analysis.

Selected-folder summaries add exact-component name hints for `.build`, `DerivedData`, `node_modules`, `.npm`, `.pnpm-store`, `.yarn`, `.venv`/`venv`, `__pycache__`, `.gradle`, `.m2`, `.cargo`, `target`, `Pods`, `Carthage`, `CoreSimulator`, and `Docker`. These labels describe common development-storage locations; they do not inspect contents, infer application ownership, assess reproducibility, or recommend deletion. Similar names do not match.

The scan is not an atomic filesystem snapshot. Disker checks that opened directories match the identity discovered during enumeration, compares directory metadata before and after reading each directory, and rechecks regular-file metadata after enumerating each parent. Detected changes make coverage partial. A file can still change after its final recheck while the scanner continues elsewhere, and the tree is not frozen for the duration of a scan. A complete observation means no detected directory or file changes, metadata/access failures, or excluded symlinks; it is not a transactional snapshot guarantee.

Folder-history comparisons and charts use the same selected path and complete observations through the current observation. The chart shows up to 24 samples from that path; incomplete scans and future observations are not plotted. Directory-history comparisons additionally require the same root-relative directory path and complete root and subtree coverage in both observations. An arithmetic overflow suppresses a delta. Deltas and charts describe allocated-byte estimates, not reclaimable space.

## Duplicate verification

Duplicate review is a separate, user-confirmed operation. The user selects exact folders, sees those paths in a confirmation dialog, and authorizes content reads. Disker first groups regular files by logical size and hashes only groups with multiple distinct `(device, inode)` identities. Directory and file opens are descriptor-relative with no-follow flags; file identity, type, size, allocated blocks, modification time, and change time are checked before and after hashing. After all reads, Disker also rechecks metadata for every regular file in the selected scope, including files already hashed, to catch later in-place changes while other files were being read. Paths that changed or became unavailable are removed before groups are reported, and groups with fewer than two still-valid files are suppressed. Directory metadata is compared around enumeration and checked again after hashing to catch many later entry changes. This is not an atomic filesystem snapshot, and files can still change after verification completes. Read failures, symlinks, special files, detected changes, and cancellation leave the result incomplete. Only SHA-256-matched groups and their exact paths are reported in the current session; hashes are not persisted. Identical contents do not prove that removal is safe or estimate reclaimable APFS space. A read-only dry-run plan can list exact non-preserved paths only after the user chooses which verified copy to keep; it retains the original verification time and warns users to recheck before taking action, marks risk and reclaimable bytes unknown, records selected-scope coverage, and provides no execution control.

## Persistence and privacy

The confirmed history-clear action also cancels an in-flight folder scan and invalidates its generation. A scan result or memory-pressure callback already queued before the clear cannot write into the next history generation. If cancellation cannot stop traversal immediately, its eventual result is discarded.

The About page offers a manual, in-memory metadata scan of only `Bundle.main.bundleURL` and the app's dedicated `Application Support/Disker` folder when that folder exists. It reveals each measured path in Finder, stores no growth observation, and excludes user-selected roots. Clearing history cancels this scan and invalidates its result so the displayed local-data size cannot survive the clear.

The app writes at most 180 root-volume capacity observations, 180 folder-scan observations, 180 manual or active-session RAM observations, and 180 application-to-folder association records to `~/Library/Application Support/Disker/observations.json`. The containing directory is owner-only (`0700`) and the observations file is owner-readable/writable (`0600`) to limit exposure of selected paths and process names to other local accounts. Each capacity sample stores the macOS volume name, UUID, and local/network flag when provided by Foundation. Capacity series require the same capacity size, availability API basis, and volume UUID when both samples have one; a transition between legacy samples without a UUID and identified samples starts a fresh series. The UI labels the system volume by its reported name and whether macOS reports it as local, without claiming a physical device or SSD identity. Each association retains at most 50 folder paths. Up to 20 user-selected folder or application-bundle permissions are held separately in `selected-scopes.json`; these are read-only security-scoped bookmarks, stored locally with owner-only file permissions. They exist only to support a later user-triggered rescan. Disker does not schedule storage scans, access saved scopes at launch, or monitor folders in the background. Users can forget individual scopes or clear them with local history. Clearing history cancels pending RAM persistence, stops pressure-event observation, and disables the active-session sampling toggle. Capacity observations are taken on app open, after a folder scan, or after an explicit Refresh action, not on a background schedule. The overview plots up to 24 observations from the latest comparable series; its focused vertical scale is labeled, and a capacity delta still makes no attribution to folders. Capacity deltas report only system-reported available-space change. Storage scans store paths and sizes, not file contents. RAM samples contain aggregate page counts plus the names, PIDs, and resident-size measurements of the ten largest processes. Duplicate checks do not persist file contents or hashes. No network or telemetry code is present.

## RAM sampling

`RAMObservation` samples physical RAM size, free/active/inactive/wired/compressor page counts via Mach host statistics and converts each count using the kernel page size. It separately samples process resident sizes and kernel process start times using `proc_listallpids`, `proc_pidinfo`, and `proc_name`. An optional `vm.swapusage` sysctl sample records current total, available, and used swap bytes; a successful all-zero result means no swap is currently allocated, while a failed or malformed result remains unavailable. Sampling is manual by default. The user can opt into five-minute RAM samples and a public Dispatch memory-pressure source while Disker is the active app; samples pause when it becomes inactive, overlapping RAM requests are suppressed, and the toggle resets off on next launch. The source records only `normal`, `warning`, or `critical` transitions that macOS reports while enabled. It supplies no guaranteed initial state, so the UI labels gaps and periods before an observed event unknown rather than carrying the last state forward. Pressure events are kept in a separate bounded list of 180 observations. No background service is installed. Up to 180 RAM observations are retained locally and the UI plots the latest 24 free and compressed page counts plus swap use where reported. A possible process-growth signal requires a continuous run of at least three available observations for the same PID, name, and kernel start time, spanning at least 15 minutes and growing by 100 MiB or more. At a five-minute cadence it can use four samples. It is an investigation signal only. Process exit or access restrictions are counted as unavailable. Inactive pages can be reclaimable cache; page groups are not a single additive pressure metric. Process resident size is not physical footprint. Continuous pressure sampling and leak diagnosis are not implemented.

## Not implemented

Automatic application/project ownership discovery, broad cleanup discovery and execution, storage activity monitoring, background scans, continuous RAM pressure baselines, leak diagnosis, an App Store-ready sandbox build, Developer ID signing/notarization, and an installer. A separate ad-hoc sandbox configuration probe exists, but its selected-folder and bookmark workflows are not validated. RAM sampling is limited to on-demand snapshots plus optional active-app sampling and pressure transition events. The only cleanup plan supported is a read-only dry run derived from verified duplicates and an explicit keeper selection; it is not a general cleanup plan and performs no operation.

## Distribution and sandbox constraints

Apple requires App Sandbox for Mac App Store distribution. The separate local probe requests App Sandbox, read-only access to user-selected files, and app-scoped bookmarks for explicitly selected scopes. Apple documents the [`com.apple.security.files.bookmarks.app-scope` entitlement](https://developer.apple.com/documentation/professional-video-applications/enabling-security-scoped-bookmark-and-url-access) for persistent app-scoped bookmark access. macOS grants the selected folder's scope, including descendants; Disker calls `startAccessingSecurityScopedResource()` while each scan or duplicate check runs and stops access when it finishes. Saved bookmarks are bounded to 20, can be individually removed, refreshed when a stale bookmark resolves, and are never opened automatically. The ad-hoc probe launched and its entitlements verified, but bookmark creation, resolution, stale-bookmark refresh, scope balancing, and protected-folder failure states remain unvalidated.

The ordinary development bundle remains unsigned and unsandboxed; the separate ad-hoc sandbox probe is not a release signature or App Store-ready build. Selected-folder traversal, duplicate reads, local history placement, and protected-folder failure states remain to be validated under the sandbox. macOS may still deny access because of file permissions, ACLs, system protections, or data-protection rules. Disker must surface those cases as incomplete coverage. It must not claim whole-volume visibility or attempt to grant itself Full Disk Access. See Apple's [App Sandbox](https://developer.apple.com/documentation/security/app-sandbox), [accessing files from the macOS App Sandbox](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox), and [NSOpenPanel](https://developer.apple.com/documentation/appkit/nsopenpanel) documentation.
