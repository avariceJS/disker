# Architecture

## Modules

- `DiskerCore` contains storage measurements, selected-folder scanning, bounded history, and bounded selected-scope bookmarks.
- `DiskerApp` is a native SwiftUI macOS application with an `NSOpenPanel` for user-selected scan scope and Finder reveal.
- `DiskerCoreChecks` is a small executable check suite using temporary synthetic trees and a synthetic `.app` Info.plist; run it with `scripts/check-core.sh`.

## Measurement contract

Volume total and available capacity are separate system-provided values. Disker prefers macOS's important-usage availability estimate when it is positive; if it is zero/unavailable, it falls back to the standard volume available-capacity value and labels that basis. Disker derives `notAvailableBytes = total - available`; it does not call this physical file usage because reservations and APFS/macOS accounting are not attributable to a path scan.

Folder scans open selected directories and descend with descriptor-relative `openat` and `fstatat`, always using `O_NOFOLLOW`/`AT_SYMLINK_NOFOLLOW` for descendants. This avoids following a child directory replaced by a symlink during a scan. Disker verifies that an opened directory still has the device/inode identity seen during enumeration and compares directory link count, modification time, and change time before and after listing. If that evidence changes, the affected subtree and root are marked partial with a separate changed-during-scan count. This catches some directory-entry races, not every write to a file after its metadata was sampled. Symlinks are not traversed; a selected symlink root is reported as incomplete. Each `(device, inode)` is counted once per selected root. Logical bytes are `st_size`; allocated bytes are `st_blocks * 512`. These estimates can diverge from reclaimable space because clones and shared blocks are not attributed. A failed metadata lookup or directory access marks that root incomplete.

Each folder scan records the selected path, observation time, logical and allocated estimates, file count, inaccessible count, excluded symlink count, and completion state. It also stores at most the 100 largest descendant-directory summaries. These are overlapping subtree totals and are explicitly presented as non-additive. A direct `.git` directory is additionally retained as a selected-root-relative measurement even when it falls outside that ranking; a `.git` file remains only a marker, and a symlink is skipped. Git metadata comparisons require the same selected root and `.git` relative path plus complete observations. A directory's coverage is incomplete when an inaccessible item or excluded symlink lies within its subtree. Hard-linked bytes are assigned to the UTF-8 lexicographically first relative file path, making sibling directory attribution deterministic.

The native folder picker and scan entry point cap each observation at 50 selected roots, matching the existing maximum app-folder association count. Over-limit selections are rejected before bookmark creation or scanning so one observation cannot grow without bound from an accidental bulk selection.

The overview's folder-growth highlights are the largest three positive allocated-byte deltas for each path's latest complete scan against its previous complete scan. Paths are never compared across roots. A newer partial scan suppresses that path's older signal, and shrinking or unchanged paths are omitted. These highlights are historical selected-path evidence, not a claim that a folder caused a system-capacity change.

For project context, Disker flags a selected directory when it contains a direct, non-symlink `.git` entry. A direct `.git` directory's file-tree metrics are surfaced as “Git metadata in this selected folder”; this narrow measurement is not project ownership or reclaimable-space attribution. Disker does not read a `.git` file, claim project ownership, or infer that the repository's contents are disposable. Nested repository markers are attached only to their immediate containing directory.

The Applications view offers an `NSOpenPanel` restricted to application bundles and measures only the explicitly chosen `.app` tree. During this explicit app-selection flow, Foundation reads the selected bundle's declared `CFBundleIdentifier` from its `Info.plist`; Security reads the embedded App Groups claims and [`SecStaticCodeCheckValidity`](https://developer.apple.com/documentation/security/code-signing-services) performs strict local signature validation. This may read signed executable and resource contents locally, runs off the main thread, and never uploads them. It verifies local code integrity, not Gatekeeper/notarization trust or publisher identity. The generic folder-size scanner still reads filesystem metadata only. The declared ID, embedded group claims, signature-validation result, and signed identifier are stored with that bundle's observation. To keep local history bounded against pathological bundle metadata, Disker ignores a claim list with more than 256 entries or 64 valid unique group IDs, and ignores IDs longer than 255 bytes. When the user later associates an exact folder path, a matching signed identifier receives a stronger match label for the selected user's `~/Library/Containers/<bundle-id>` directory or a descendant; a matching ID from an unvalidated signature remains probable. A path under `~/Library/Group Containers/<group-id>` receives a signed shared-group label only when the signature validates, its signed identifier matches the declared ID, and its embedded entitlement lists that exact group ID. Otherwise, a matching embedded claim is labeled declared and unvalidated. App-group data is shared; neither label implies current use or exclusive ownership. All other links remain labeled user-selected and unverified. History indexes only selected roots whose path has an `.app` extension. The user can separately choose folders and associate them with that exact bundle path; Disker stores up to 180 associations with at most 50 paths per app and rejects an over-limit addition without dropping prior links. Each path's measurements are shown separately, never summed, because paths may overlap or be shared. Removing a relationship changes only Disker's local metadata; clearing history also clears the associations. Bundle contents can include excluded symlinks, which leave the estimate partial. Unselected support folders, caches, containers, and shared dependencies are not discovered; there is no uninstall operation or consequence analysis.

Selected-folder summaries add a small set of exact-component name hints for `.build`, `DerivedData`, `node_modules`, `.venv`/`venv`, and `__pycache__`. These labels describe common development-storage locations; they do not inspect contents, infer application ownership, assess reproducibility, or recommend deletion. Similar names do not match.

The scan is not an atomic filesystem snapshot. Disker checks that opened directories match the identity discovered during enumeration and compares directory metadata before and after reading each directory. Detected changes make coverage partial. This does not detect every file-content write that races with metadata sampling, and the tree is not frozen for the duration of a scan. A complete observation means no detected directory changes, metadata/access failures, or excluded symlinks; it is not a transactional snapshot guarantee.

Folder-history comparisons and charts use the same selected path and complete observations through the current observation. The chart shows up to 24 samples from that path; incomplete scans and future observations are not plotted. Directory-history comparisons additionally require the same root-relative directory path and complete root and subtree coverage in both observations. An arithmetic overflow suppresses a delta. Deltas and charts describe allocated-byte estimates, not reclaimable space.

## Duplicate verification

Duplicate review is a separate, user-confirmed operation. The user selects exact folders, sees those paths in a confirmation dialog, and authorizes content reads. Disker first groups regular files by logical size and hashes only groups with multiple distinct `(device, inode)` identities. Directory and file opens are descriptor-relative with no-follow flags; file identity, size, modification time, and change time are rechecked before and after hashing. Directory metadata is compared around enumeration and checked again after hashing to catch many later entry changes. This is not an atomic filesystem snapshot. Read failures, symlinks, special files, detected changes, and cancellation leave the result incomplete. Only SHA-256-matched groups and their exact paths are reported in the current session; hashes are not persisted. Identical contents do not prove that removal is safe or estimate reclaimable APFS space. A read-only dry-run plan can list exact non-preserved paths only after the user chooses which verified copy to keep; it marks risk and reclaimable bytes unknown, records selected-scope coverage, and provides no execution control.

## Persistence and privacy

The app writes at most 180 root-volume capacity observations, 180 folder-scan observations, 180 on-demand RAM observations, and 180 application-to-folder association records to `~/Library/Application Support/Disker/observations.json`. Each association retains at most 50 folder paths. Up to 20 user-selected folder or application-bundle permissions are held separately in `selected-scopes.json`; these are read-only security-scoped bookmarks, stored locally with owner-only file permissions. They exist only to support a later user-triggered rescan. Disker does not schedule scans, access saved scopes at launch, or monitor folders in the background. Users can forget individual scopes or clear them with local history. Capacity observations are taken on app open, after a folder scan, or after an explicit Refresh action, not on a background schedule. The overview plots up to 24 observations from the latest run with the same total capacity and macOS availability method; its focused vertical scale is labeled, and a capacity delta still makes no attribution to folders. Capacity deltas report only system-reported available-space change. Storage scans store paths and sizes, not file contents. RAM samples contain aggregate page counts plus the names, PIDs, and resident-size measurements of the ten largest processes. Duplicate checks do not persist file contents or hashes. No network or telemetry code is present.

## RAM sampling

`RAMObservation` samples physical RAM size, free/active/inactive/wired/compressor page counts via Mach host statistics and converts each count using the kernel page size. It separately samples process resident sizes and kernel process start times using `proc_listallpids`, `proc_pidinfo`, and `proc_name`. Sampling is manual and point-in-time; up to 180 observations are retained locally and the UI plots the latest 24 free and compressed page-count measurements. A possible process-growth signal requires the same PID, name, and start time in three consecutive process-list samples spanning at least 15 minutes and growing by 100 MiB or more. It is an investigation signal only. Process exit or access restrictions are counted as unavailable. Inactive pages can be reclaimable cache; page groups are not a single additive pressure metric. Process resident size is not physical footprint. System memory-pressure trends, swap, and leak diagnosis are not implemented.

## Not implemented

Application/project ownership attribution, broad cleanup discovery and execution, activity monitoring, automatic scans, RAM pressure/swap trends, leak diagnosis, sandbox entitlements, signing/notarization, and an installer. The only cleanup plan supported is a read-only dry run derived from verified duplicates and an explicit keeper selection; it is not a general cleanup plan and performs no operation.

## Distribution and sandbox constraints

Apple requires App Sandbox for Mac App Store distribution. A sandboxed edition can request the least privilege needed here: user-selected read-only file access through an open panel. macOS grants the selected folder's scope, including descendants; Disker calls `startAccessingSecurityScopedResource()` while each scan or duplicate check runs and stops access when it finishes. For selected folder scans, Disker can save an explicit read-only bookmark so the user can request another scan after relaunch without choosing the path again. Saved bookmarks are bounded to 20, can be individually removed, refreshed when a stale bookmark resolves, and are never opened automatically. A signed sandboxed build still needs to validate bookmark creation, resolution, stale-bookmark refresh, scope balancing, and protected-folder failure states.

The development bundle is unsigned and has no App Sandbox entitlement; this is not evidence of App Store readiness. A signed sandboxed build must validate selected-folder traversal, duplicate reads, local history placement, and protected-folder failure states. macOS may still deny access because of file permissions, ACLs, system protections, or data-protection rules. Disker must surface those cases as incomplete coverage. It must not claim whole-volume visibility or attempt to grant itself Full Disk Access. See Apple's [App Sandbox](https://developer.apple.com/documentation/security/app-sandbox), [accessing files from the macOS App Sandbox](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox), and [NSOpenPanel](https://developer.apple.com/documentation/appkit/nsopenpanel) documentation.
