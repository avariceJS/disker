# Architecture

## Modules

- `DiskerCore` contains storage measurements, selected-folder scanning, bounded history, and bounded selected-scope bookmarks.
- `DiskerApp` is a native SwiftUI macOS application with an `NSOpenPanel` for user-selected scan scope and Finder reveal.
- `DiskerCoreChecks` is a small executable check suite using temporary synthetic trees and a synthetic `.app` Info.plist; run it with `scripts/check-core.sh`.

## Measurement contract

Volume total and available capacity are separate system-provided values. Disker prefers macOS's important-usage availability estimate when it is positive; if it is zero/unavailable, it falls back to the standard volume available-capacity value and labels that basis. Disker derives `notAvailableBytes = total - available`; it does not call this physical file usage because reservations and APFS/macOS accounting are not attributable to a path scan.

The Overview shows a low-availability review signal when available capacity falls below the larger of 10 GiB or 5% of the reported total. This threshold is a dashboard heuristic, not an alert, usage attribution, or estimate of reclaimable space.

Unsandboxed folder scans walk the selected absolute root component by component from `/` using `fstatat(AT_SYMLINK_NOFOLLOW)` and descriptor-relative `openat(O_NOFOLLOW)`. Sandboxed scans cannot open `/` because their authority is limited to the selected bookmark; while that scope is active they inspect each path prefix with `lstat`, reject observed symlink ancestors and final symlinks, open the selected directory with `O_NOFOLLOW`, and recheck prefix identities before enumeration. A denied or unstable prefix fails closed as incomplete. In both modes raw `.`/`..` components and directory identity changes are rejected. A selected regular-file root is inspected with no-follow metadata only and is never opened or read. Directory roots are reopened and identity-checked after enumeration; selected file roots receive final metadata revalidation after other selected roots have been scanned. Descendants are traversed with descriptor-relative no-follow operations. Disker verifies that an opened directory still has the device/inode identity seen during enumeration, compares directory link count, modification time, and change time before and after listing, and rechecks regular-entry identity, type, size, allocated blocks, modification time, and change time after enumerating each parent. Samples of hard-linked paths are also compared by inode across directories; observing different versions makes coverage partial and permanently withholds that object's modification date for the observation. If that evidence changes, the affected subtree and root are marked partial with a separate changed-during-scan count. This catches many directory-entry and in-place file mutation races, but cannot freeze the tree or detect every change after an entry's final recheck. Symlinks are not traversed; a selected symlink root is reported as incomplete. Nested entries whose `st_dev` differs from the selected root are not descended into or counted, and the root and affected directory summaries record an excluded volume-boundary count; the user can select that volume as its own root. Only regular files contribute to file size and filename-extension totals. Sockets, FIFOs, device nodes, and other special filesystem entries are excluded and separately reported as incomplete coverage for their containing subtree and selected root. Each regular `(device, inode)` is counted once per selected root. Logical bytes are `st_size`; allocated bytes are `st_blocks * 512`. These estimates can diverge from reclaimable space because clones and shared blocks are not attributed. A failed metadata lookup or directory access marks that root incomplete. Selected paths that pass through system aliases such as `/var` fail closed as incomplete when the alias is a symlink; a native picker may return a canonical path that avoids the alias.

Scan progress reports the latest path after every 256 traversed directory entries and whenever 256 additional unique regular-file objects have been counted. The displayed file-object count deduplicates hard links; entry-based updates ensure a large tree of empty directories still reports progress.

File metadata revalidation remains cancellable one file at a time. If cancellation interrupts that pass, the scan remains partial and modification dates for unverified entries are withheld; measured byte totals are retained as partial observations.

Each folder scan records the selected path, the root's no-follow `st_dev` device identifier, observation time, logical and allocated estimates, file count, inaccessible count, excluded symlink and nested-volume-boundary counts, and completion state. It also retains at most 32 deterministic, root-relative paths of excluded symlink entries so the user can locate incomplete areas; excess entries are omitted with an explicit truncation flag. Disker never reads a link target or traverses the link. Folders detail can reveal a listed link entry in Finder, and instructs the user to select any desired target independently. A nested volume boundary is excluded from the selected root's totals and makes coverage partial. The device identifier helps prevent a different mounted volume at the same path from being compared as growth; older history without an identifier is compared only with other observations that also lack one. It is not a persistent disk serial number. The scanner revalidates a selected directory's path identity after enumeration and marks coverage partial if the root disappears or changes. It stores at most the 100 largest descendant-directory summaries and, independently, the 20 largest nested directories with either a direct regular `.git` entry or an exact recognized development-data directory name. The dashboard retains at most 20 regular-file summaries, ranked by `st_blocks * 512`, with separate logical and allocated values and the file's filesystem modification time. That time is descriptive metadata, not last use or cleanup evidence, and is withheld if final no-follow metadata revalidation fails or detects a changed file. These summaries remain bounded and their Finder reveal only targets a path within the selected root. Directory totals overlap and are explicitly presented as non-additive. A direct `.git` directory is additionally retained as a selected-root-relative measurement even when it falls outside that ranking; a direct `.git` file remains only a marker, and symlinks and special entries are not repository markers. Named development-data entries are candidates based on the directory's own final component; ancestor names do not turn every descendant into a candidate. The UI labels nested paths as repository or development-data candidates without claiming verified project ownership or safe cleanup. Their history is compared only for the same selected root, matching device identifier when available, and exact relative path across complete observations. Git metadata comparisons require the same selected root and `.git` relative path plus complete observations. A directory's coverage is incomplete when an inaccessible item or excluded symlink or volume boundary lies within its subtree. Hard-linked bytes are assigned to the UTF-8 lexicographically first relative file path, making sibling directory attribution deterministic.

Full file-level storage change tracking uses a separate local inventory store rather than embedding hundreds of thousands of paths in every bounded chart observation. A complete selected-root scan stores the no-follow regular-file path inventory, with one deterministic path per hard-linked file object and separate logical and allocated estimates, ordered by UTF-8 relative path. Comparison uses a merge walk over the two ordered inventories and retains only the top 100 path changes while computing exact net logical and allocated deltas plus separate gross positive and negative allocated deltas. These allocated values are estimates, not reclaimable physical space. A bounded aggregate timeline retains up to 120 comparable intervals per root and 2,400 total, with no repeated path lists; the latest eight are available in the Folders detail. The latest detailed path report alone retains up to 100 changed paths. The store is capped at 500,000 entries per root and 750,000 entries total across at most 50 roots; the binary property-list store is capped at 128 MiB. Snapshot format v2 stores each sorted manifest as a streaming LZFSE-compressed payload of UTF-8 relative paths and logical/allocated byte counts, so the dashboard decodes summaries without expanding path lists and recording expands only the prior manifest for the selected root. Legacy v1 snapshots are converted one root at a time when a complete inventory is next recorded, then atomically replaced by v2; a failed conversion or corrupt payload leaves the prior store untouched. Expanded payload, entry-count, path-length, root-count, and total-entry bounds are validated before comparison. Inaccessible entries, concurrent mutations, a selected-root identity change (including replacement by a symlink), nested volumes, special files, cancellation, accounting overflow, or inventory truncation suppress baseline replacement and comparison. Symlink entries remain excluded, but nested symlinks do not invalidate regular-file inventory completeness within the selected no-follow scope; the UI states that symlink targets were not followed. A first complete scan creates only a baseline. Later complete scans compare every retained regular-file path with the prior baseline for the exact selected root and matching device identifier. A changed volume clears that root's aggregate timeline. New or absent paths do not prove creation or deletion: moves, renames, restores, and replacements can produce similar evidence. Changes between scans that leave no on-disk difference are not detected.

The Folders page offers an on-demand SQLite sidecar review only when the current folder observation matches a saved complete file inventory. `FileInventoryStore.loadSnapshot(for:matchingObservationID:)` decodes only the selected root's packed payload, off the render path, and rejects missing, incomplete, or stale observations. `DatabaseSidecarReview` links only exact same-directory filename pairs (`.db`, `.sqlite`, or `.sqlite3` with `-wal`, `-shm`, or `-journal`). It displays each file's logical and allocated estimates independently, caps the review at 200 matched groups and 200 unmatched sidecar-name candidates, and discloses excluded symlinks. When the exact root, observation, known volume ID, and baseline timestamp match a complete file-change report, each current path can show its logical and allocated-estimate delta. The report's omitted count is validated against its retained rows; a missing path means no measured size change only when no rows were omitted. Otherwise its change remains unknown. A missing peer path in a complete selected-root inventory is not evidence of an orphan or unused database; all associations remain filename clues. Each listed file can be revealed in Finder without opening its contents. No database contents are read or parsed.

The Overview's unrecovered-capacity-loss context also checks retained file-inventory trend points whose complete scan interval overlaps that capacity interval within the same 60-second boundary tolerance. It can show gross selected-root file growth even when directory totals are partial, such as when symlink targets were excluded. This is temporal context only: the selected root may be on a different volume, and the correlated change does not establish cause. The UI exposes excluded symlink counts and keeps unselected, inaccessible, and system-managed usage unknown.

Explicitly opted-in saved roots may use macOS File System Events while the Disker window remains open, regardless of which app is foregrounded. An event requests a debounced full metadata scan only after at least five minutes have passed since that root's latest full scan in the current process, regardless of whether that scan was manual, scheduled, or event-triggered. The user-selected periodic full scan remains as reconciliation; the shared minimum matches the fastest periodic cadence and avoids back-to-back full scans. The event stream is a prompt to inspect the current tree, not a complete event journal: events can be coalesced or dropped, and a file created and removed between full scans cannot be reconstructed. Monitoring consent is stored separately from bookmarks in a bounded owner-only preference file; only paths that still have an exact saved bookmark are eligible. On the next window open, opted-in roots resume and the scheduler reconciles any interval since the last complete inventory. Bookmark scopes are resolved only for these previously opted-in roots and only while the window is open. Closing the window or quitting stops scans until the next launch. If event setup fails, Disker reports the issue and retains periodic scanning. No helper, persistent service, file-content read, or system-wide watch is used. A partial scan leaves the last valid baseline untouched and its report is labeled stale against the current observation.

Overview, History, Folders, saved-root details, and app-footprint rows label partial aggregates as measured so far and state that the total is unknown. If a partial scan measures no bytes, the UI says “No bytes measured · total unknown” and shows an unknown allocated value instead of formatting zero as the folder's size.

Folder observations retain at most 30 filename-extension aggregates, ordered by allocated-byte estimate. The Overview shows the five largest retained categories. Extension parsing uses only the last filename component, lowercases safe ASCII extensions up to 32 bytes, and groups extensionless, unusual, or longer values into bounded labels. It never reads content or verifies file type or purpose. A hard-linked file object is assigned the extension of its deterministic retained path. When more than 30 categories occur, the observation retains their combined logical bytes, allocated-byte estimate, and file count in a separate “other extensions” aggregate, so the bounded category detail still reconciles to the measured file totals. The Folders detail combines its five largest categories with all remaining retained and omitted categories into a bounded, interactive Swift Charts donut. A compact segmented control switches the chart between logical bytes and allocated-byte estimates without combining the metrics; selecting a sector or its legend button reveals the category's active value and file count, while the legend retains both values side by side. The Applications detail reuses the same chart in a collapsed disclosure for a measured `.app` bundle. The chart is withheld for byte-accounting overflow or legacy truncated observations without the omitted-category aggregate; on partial observations it explicitly describes measured entries only. It does not imply a complete folder total, content type, ownership, or reclaimable space. The remainder is not treated as a stable extension for history comparisons. For the latest complete scan of an exact selected root, Disker can show positive category-level allocated-estimate deltas against its previous complete scan. It suppresses that comparison if either scan is partial, a newer partial scan exists, old history lacks categories, or either category list was truncated. Extension categories are metadata summaries, not cleanup or safety signals.

Visible extension categories may also receive a filename-only artifact clue for common database/SQLite sidecar, log, archive/installer, model/checkpoint, and structured-data extensions. These labels are not a content or ownership check and do not imply that a file is disposable or regenerable.

The native folder picker and scan entry point cap each observation at 50 selected roots, matching the existing maximum app-folder association count. Over-limit selections are rejected before bookmark creation or scanning so one observation cannot grow without bound from an accidental bulk selection.

When a scan contains identical selected paths or a lexical parent/child pair, Overview and Folders warn that root totals can include the same files and must not be added together. The comparison normalizes path syntax and checks component boundaries; it does not resolve symlinks, aliases, or filesystem identity.

The overview's folder-growth highlights are the largest three positive allocated-byte deltas for each path's latest complete scan against its previous complete scan. Paths are never compared across roots. A newer partial scan suppresses that path's older signal, and shrinking or unchanged paths are omitted. These highlights are historical selected-path evidence, not a claim that a folder caused a system-capacity change.

Overview retains the largest comparable system-reported available-space drop of at least 100 MiB in the bounded history that has not subsequently recovered to its pre-drop level. Smaller later losses do not hide a still-unrecovered larger drop. It can show selected-root growth whose complete same-path comparison overlaps that exact interval. Either comparison endpoint may sit within 60 seconds of the corresponding capacity boundary to account for the normal scan-then-capacity sampling order. The pair must satisfy the normal selected-root and volume comparison rules; out-of-window, partial, missing, or unchanged observations produce no growth entry. A prominent source-unknown status and exact-folder chooser appear when no selected scans align. The UI explains that capacity alone cannot name changed files or their size and a new scan cannot reconstruct a pre-scan baseline. When the latest selected-root scans are partial, it shows their measured-size estimates, coverage exclusions, and clarifies that these are not new bytes. When aligned growth exists, the UI shows actual scan timestamps and warns that the full growth may have happened at another time. Overlapping selected roots remain separate and non-additive. This timing context does not claim that measured folders caused the system-reported capacity change or account for unselected and system-managed storage.

The overview separately highlights up to three growing descendant paths. A directory is compared only with the same relative path under the same selected root and the previous complete observation. The path must appear in both retained summaries; an omitted path is not interpreted as zero even when a top-directory summary was truncated. A newer partial root scan suppresses older signals. These are allocated-byte estimates and do not establish project ownership.

To keep the Overview concise, it shows only the three largest roots with summary metrics. The Folders page remains the place for per-root histories, filename categories, Git metadata, and retained descendant details.

For project context, Disker flags a selected directory when it contains a direct, non-symlink `.git` entry. A direct `.git` directory's file-tree metrics are surfaced as “Git metadata in this selected folder”; this narrow measurement is not project ownership or reclaimable-space attribution. Disker does not read a `.git` file, claim project ownership, or infer that the repository's contents are disposable. Nested repository markers are attached only to their immediate containing directory.

The bounded `ProjectCandidateInventory` projects direct selected-root Git markers and nested Git-marked directory summaries from the newest retained observation per selected directory. It starts no filesystem query, uses no Spotlight result, and presents up to 100 exact-path candidates with at most five selected-scope provenance rows each. A case-insensitive name/path filter searches saved selected-folder observations before applying the display cap, so candidates beyond the first 100 can be found without widening filesystem access. The projection retains at most 101 sorted candidate paths and source accumulators only for those paths; SwiftUI builds it in a utility-priority detached task rather than during body evaluation, forwards task cancellation into the projection, and only publishes results for the current history key. The latest-root index still scales with the number of distinct selected roots. Latest partial observations replace older evidence; partial/cancelled coverage and the scanner's 20-candidate summary cap remain visible, so an omitted marker is unknown rather than removed. Parent-scan logical bytes and allocated estimates remain attributed to that parent observation and are never added to standalone project measurements. Existing explicitly tracked project roots are retained in the list even when no candidate observation is available.

Tracking a discovered candidate requires a native picker confirmation of the same standardized directory. `ProjectRootMarkerProbe` opens each absolute path component with `O_NOFOLLOW` and inspects only the direct `.git` entry with `fstatat(AT_SYMLINK_NOFOLLOW)`; it accepts a real `.git` directory or regular worktree marker, rejects symlinks in every path component, and reads no contents. Tracking creates or reuses an empty `ProjectResourceAssociation`, attempts to save the selected-root bookmark, and starts the normal independent metadata-only scan. The resulting selected-root history remains exact-path and complete-observation only. Stopping tracking removes only an association with no explicit linked locations; links, observations, bookmarks, and files are preserved.

Folders detail can record a user-authored relationship between a selected root with a direct `.git` marker and up to 50 additional paths. The user chooses those exact paths and explicitly starts their metadata-only scan; each path receives its own local observation and bookmark. `ProjectResourceAssociation` is capped at 100 roots and is stored in the bounded local observation history. The read-only `ProjectResourceReview` joins only the newest observation for each exact path, including a newer partial observation, and exposes missing, partial, overlapping, and linked-from-another-project evidence without calculating a project subtotal. A link is user-provided context, not ownership, exclusive use, or shared-block attribution. Comparisons remain exact-path and complete-observation only. Removing a relationship leaves files and scan history untouched; clearing local history removes the association with the rest of Disker's local records.

`ProjectResourceGrowthReview` derives one latest growth row per project-root or explicitly linked path from `ProjectResourceReview` and the bounded scan history. It builds one path index, then compares only a complete, non-cancelled, non-overflowed latest observation with the nearest prior complete non-cancelled observation of the same exact path and volume, with strictly increasing timestamps and checked logical/allocated deltas. Latest partial or cancelled scans suppress stale comparisons. Missing baselines, volume changes, timestamp disorder, and overflow are represented as explicit statuses. The Folders disclosure shows each interval, logical delta, allocated-byte estimate delta, and complete selected-path coverage separately. It caps the compact display at eight comparisons and links users to the existing per-path chart and file-change details; it never calculates a project total, aligns unrelated intervals, or claims cause, ownership, or reclaimable space. It expands no file-inventory manifests and performs no additional filesystem reads.

The Applications view offers an `NSOpenPanel` restricted to application bundles and measures only the explicitly chosen `.app` tree. Because AppKit may present packages as directories, the picker allows both file and directory selection while filtering for `UTType.applicationBundle`; after selection, Disker requires a `.app` extension, uses `lstat` to reject a symlink or non-directory root, then validates `CFBundlePackageType == APPL` and a nonempty bundle identifier before measurement. During this explicit app-selection flow, Foundation reads the selected bundle's declared `CFBundleIdentifier` from its `Info.plist`; Security reads the embedded App Groups claims and [`SecStaticCodeCheckValidity`](https://developer.apple.com/documentation/security/code-signing-services) performs strict local signature validation. This may read signed executable and resource contents locally, runs off the main thread, and never uploads them. It verifies local code integrity, not Gatekeeper/notarization trust or publisher identity. The generic folder-size scanner still reads filesystem metadata only. The declared ID, embedded group claims, signature-validation result, and signed identifier are stored with that bundle's observation. A separate persisted flag records that a root came through the restricted app-bundle picker; the Applications list does not classify arbitrary selected directory names ending in `.app` as applications. Once a path is classified by explicit selection, the list uses its newest same-path measurement, including later saved-folder scans; signature and identity evidence are never copied forward from older scans. Older history with a stored bundle identifier retains this classification; older observations without one remain unclassified. To keep local history bounded against pathological bundle metadata, Disker ignores a claim list with more than 256 entries or 64 valid unique group IDs, and ignores IDs longer than 255 bytes. When the user later associates an exact folder path, a matching signed identifier receives a stronger identifier-plus-conventional-path label for the selected user's `~/Library/Containers/<bundle-id>` directory or a descendant; the folder's origin, current use, and exclusive ownership are not established. Exact bundle-ID-named descendants under `~/Library/Application Support` and `~/Library/Caches` receive only a weak name-match label, because those locations do not encode a verified ownership relationship. A path under `~/Library/Group Containers/<group-id>` receives a signature-covered shared-claim label only when the signature validates, its signed identifier matches the declared ID, and its embedded entitlement lists that exact group ID. This is a more specific claim label, not proof of developer trust or OS-granted access. Otherwise, a matching embedded claim is labeled declared and unvalidated. App-group data is shared; neither label implies current use or exclusive ownership. All other links remain labeled user-selected and unverified. The user can separately choose folders and associate them with that exact bundle path; Disker stores up to 180 associations with at most 50 paths per app and rejects an over-limit addition without dropping prior links. Removing a relationship changes only Disker's local metadata; clearing history also clears the associations. Bundle contents can include excluded symlinks, which leave the estimate partial. The Applications view derives conventional per-app container, exact bundle-ID-named support/cache, and declared App Group paths as unmeasured suggestions from the selected bundle identity; it performs no filesystem lookup or scan until the user selects a folder in the native panel. Other support folders, caches, and dependencies are not discovered. There is no uninstall operation. A separate read-only removal-footprint review shows only the selected bundle and manually associated paths with their latest measurements, consequences, and overlap/shared-use warnings; its qualified disjoint-scope subtotal is documented below and it never estimates reclaimed space.

Associated application folders expose a direct rescan action. Disker reuses the saved read-only bookmark when present; otherwise it asks the user to select the same exact path before starting a new observation, so comparisons remain tied to the selected scope.

The user can request an asynchronous metadata-only availability check of an exact selected path. Disker reuses its saved read-only bookmark, if one exists, and verifies that it still resolves to that exact path before checking. When sandbox access permits, the probe walks each normalized absolute path component using `fstatat(AT_SYMLINK_NOFOLLOW)` and `openat(O_NOFOLLOW)`, comparing device and inode metadata before descending. It rejects observed ancestor and final symlinks and raw `.`/`..` components before lexical normalization. App Sandbox can grant a bookmark to a selected directory while denying access to one of its parent directories; in that case the probe opens only the exact bookmarked directory with `O_NOFOLLOW`, does not inspect descendants, and returns a distinct limited status stating that ancestor paths were not checked. Access-denied, malformed/stale/mismatched bookmark, symlink, and missing/unreachable states remain distinct instead of collapsing into “missing.” Applications uses this probe for app bundles and associated paths; Folders exposes it for selected project-resource rows. The result establishes directory availability only, never ownership, app removal, current use, or safety. Association or bookmark changes invalidate in-flight checks so stale results cannot reappear. No cleanup action is offered.

Selected-folder summaries add exact-component name hints for `.build`, `DerivedData`, Xcode `Archives`, `.xcarchive`, `dSYMs`/`.dSYM`, web build outputs `dist`/`build`/`out`/`.next`/`.nuxt`, `.turbo` cache, `coverage`, `node_modules`, `.npm`, `.pnpm-store`, `.yarn`, `.venv`/`venv`, `__pycache__`, `.gradle`, `.m2`, `.cargo`, `target`, `Pods`, `Carthage`, `CoreSimulator`, `Docker`, `models`, `checkpoints`, `datasets`, `dataset`, database/vector-store names (`database`, `databases`, `db`, `sqlite`, `chroma`, `chroma_db`, `lancedb`, `qdrant`, `weaviate`, `milvus`, `postgres`, and `mongodb`), training-artifact names (`artifacts`, `training-artifacts`, `training_artifacts`, and `runs`), and `logs`. These labels describe common development-storage locations; they do not inspect contents, infer application ownership, assess reproducibility, or recommend deletion. Similar names do not match.

The scan is not an atomic filesystem snapshot. Disker checks that opened directories match the identity discovered during enumeration, compares directory metadata before and after reading each directory, and rechecks regular-file metadata after enumerating each parent. Detected changes make coverage partial. A file can still change after its final recheck while the scanner continues elsewhere, and the tree is not frozen for the duration of a scan. A complete observation means no detected directory or file changes, metadata/access failures, or excluded symlinks; it is not a transactional snapshot guarantee.

Folder-history comparisons and charts use the same selected path, matching device identifier when available, and complete observations through the current observation. Charts can show the full bounded retained series (up to 180 observations) for that path and volume; incomplete scans and future observations are not numeric samples. A future-dated scan does not erase an observed volume change, and a complete same-root observation where a retained directory is absent remains a boundary rather than allowing older history to be bridged. Directory-history comparisons additionally require the same root-relative directory path and complete root and subtree coverage in both observations. An arithmetic overflow suppresses a delta. Deltas and charts describe allocated-byte estimates, not reclaimable space.

## Duplicate verification

Duplicate review is a separate, user-confirmed operation limited to 50 selected folders. An over-limit request is rejected before opening roots or reading file content. The user selects exact folders, after which Disker performs a no-follow metadata pass and estimates how many regular files share logical sizes and the logical bytes they represent. Without a security-scoped grant, the selected root is opened by walking every absolute path component from a directory descriptor, rejecting raw `.`/`..`, symlinks, and directory-identity races before traversal starts. With a granted selected-root scope, App Sandbox may deny access to parent directories; Disker then checks path prefixes using `lstat`, rejects observed symlink ancestors, opens only the exact selected directory with `O_NOFOLLOW`, and rechecks prefix identities before and after traversal. This prevents a symlinked ancestor from redirecting a selected root outside its displayed path while respecting the scoped boundary. A separate confirmation then lists the exact paths and estimate before any content is read; incomplete metadata coverage may undercount candidates, and files can change before hashing. Declining consent returns without hashing. The core API requires every caller to supply an explicit content-read authorization closure, so omission cannot silently authorize file reads. Progress distinguishes metadata-only traversal (entry count, current path, no file contents read), pending consent (candidate count and estimated bytes), and content hashing (bytes read and current path); both the pending-consent and content-reading phases are emitted only when at least one candidate file will be hashed. The check can be cancelled during traversal or hashing. Disker first groups regular files by logical size and hashes only groups with multiple distinct `(device, inode)` identities. Nested entries on another device from a selected root are skipped before content reads and make coverage partial; select that volume separately to include it. Descendant directory and file opens are descriptor-relative with no-follow flags; file identity, type, size, allocated blocks, modification time, and change time are checked before and after hashing. After all reads, Disker also rechecks metadata for every regular file in the selected scope, including files already hashed, to catch later in-place changes while other files were being read. Paths that changed or became unavailable are removed before groups are reported, and groups with fewer than two still-valid files are suppressed. Directory metadata is compared around enumeration and checked again after hashing to catch many later entry changes. Before reporting, Disker reopens each originally available selected root through the same no-follow path walk and compares its identity, including after cancellation; if a root was moved, replaced, symlinked, or became unavailable, coverage is partial and all duplicate groups are withheld for that observation. This is not an atomic filesystem snapshot, and files can still change after verification completes. Read failures, symlinks, special files, nested volume boundaries, detected changes, and cancellation leave the result incomplete. Only SHA-256-matched groups and their exact paths are reported in the current session; hashes are not persisted. Identical contents do not prove that removal is safe or estimate reclaimable APFS space. A read-only dry-run plan can list exact non-preserved paths only after the user chooses which verified copy to keep; it retains the original verification time and warns users to recheck before taking action, marks risk and reclaimable bytes unknown, records selected-scope coverage, and provides no execution control. A synthetic signed sandbox QA app verifies hashing within an app-owned scoped root, explicit refusal before reads, and symlink exclusion; it injects the scope grant and does not exercise a real user-selected bookmark or picker lifecycle.

Each duplicate-plan row also classifies the target and preserved path independently using exact path-component heuristics: a component ending in `.app`, the exact `.git` component, or common application-data components such as `Caches` and `Group Containers`. The UI explains possible consequences for both copies. These labels do not establish path ownership, active use, deletion safety, or reclaimable bytes; every plan entry continues to have unknown risk and no action control.

## Persistence and privacy

The confirmed history-clear action also cancels an in-flight folder scan and invalidates its generation. A scan result or memory-pressure callback already queued before the clear cannot write into the next history generation. If cancellation cannot stop traversal immediately, its eventual result is discarded.

The About page offers a manual, in-memory metadata scan of only `Bundle.main.bundleURL` and the app's dedicated `Application Support/Disker` folder when that folder exists. `DiskerFootprintScanner` checks the support root with `lstat`, omits it if absent, and leaves symlinks for the regular scanner to report as excluded. It de-duplicates identical bundle/support paths. The result reveals each measured path in Finder, stores no growth observation, and excludes neighboring or user-selected roots. Synthetic tests verify the exact root set, unchanged file contents, and symlink exclusion. It does not overlap an active folder scan or duplicate check. Clearing history cancels this scan and invalidates its result so the displayed local-data size cannot survive the clear.

The app writes at most 180 root-volume capacity observations, 180 folder-scan observations, 180 manual or active-session RAM observations, and 180 application-to-folder association records to `~/Library/Application Support/Disker/observations.json`. The containing directory is owner-only (`0700`) and the observations file is owner-readable/writable (`0600`) to limit exposure of selected paths and process names to other local accounts. Each capacity sample stores the macOS volume name, UUID, and local/network flag when provided by Foundation. Capacity series require the same capacity size, availability API basis, and volume UUID when both samples have one; a transition between legacy samples without a UUID and identified samples starts a fresh series. The UI labels the system volume by its reported name and whether macOS reports it as local, without claiming a physical device or SSD identity. Each association retains at most 50 folder paths. Up to 20 selected folder or application-bundle locations are stored separately in `selected-scopes.json` with owner-only file permissions. Sandboxed builds use read-only security-scoped bookmarks; the standard unsandboxed build uses ordinary path bookmarks, so its read-only behavior is enforced by Disker's code rather than by the OS. Bookmarks are not resolved at launch unless a root has an explicit saved monitoring opt-in; those bookmarks are resolved when the Disker window opens. ## RAM sampling

`RAMObservation` samples physical RAM size, free/active/inactive/wired/compressor page counts via Mach host statistics and converts each count using the kernel page size. It separately samples process resident sizes and kernel process start times using `proc_listallpids`, `proc_pidinfo`, and `proc_name`. An optional `vm.swapusage` sysctl sample records current total, available, and used swap bytes; a successful all-zero result means no swap is currently allocated, while a failed or malformed result remains unavailable. Sampling is manual by default. The user can opt into five-minute RAM samples and a public Dispatch memory-pressure source while Disker is the active app; samples pause when it becomes inactive, overlapping RAM requests are suppressed, and the toggle resets off on next launch. The source records only `normal`, `warning`, or `critical` transitions that macOS reports while enabled. It supplies no guaranteed initial state, so the UI labels gaps and periods before an observed event unknown rather than carrying the last state forward. Pressure events are kept in a separate bounded list of 180 observations. No background service is installed. Up to 180 RAM observations are retained locally. The RAM chart uses the shared 24-hour, 7-day, 30-day, or all-retained range selector and plots discrete points only, with the sample count and period end visible; no line implies readings between sample times. A possible process-growth signal requires a continuous run of at least three available, timestamp-monotonic observations for the same PID, name, and kernel start time, spanning at least 15 minutes and growing by 100 MiB or more. At a five-minute cadence it can use four samples. It is an investigation signal only. Process exit or access restrictions are counted as unavailable. Inactive pages can be reclaimable cache; page groups are not a single additive pressure metric. Process resident size is not physical footprint. Continuous pressure sampling and leak diagnosis are not implemented.

## Distribution and sandbox constraints

Saved scan roots provide explicit `Re-select…` recovery: the native picker must return the same standardized path before Disker replaces that bookmark and scans, so a different folder cannot inherit existing history.

Apple requires App Sandbox for Mac App Store distribution. The separate local sandboxed build requests read-only access to user-selected files and app-scoped bookmarks. Apple documents the [`com.apple.security.files.bookmarks.app-scope` entitlement](https://developer.apple.com/documentation/professional-video-applications/enabling-security-scoped-bookmark-and-url-access) for persistent app-scoped bookmark access. macOS grants the selected folder's scope, including descendants; Disker calls `startAccessingSecurityScopedResource()` while each scan or duplicate check runs and stops access when it finishes. Saved bookmarks are bounded to 20, can be individually removed, refreshed when a bookmark resolves stale, and are never opened automatically. GUI verification has covered selecting a folder with `NSOpenPanel`, scanning it, and rescanning through its saved bookmark in the same app session. After a sandboxed app relaunch, the prior selected-root and history display returned; actually rescanning that root through its saved bookmark after relaunch, stale-bookmark refresh, protected-folder failure states, and scope balancing still need direct validation.

The ordinary development bundle is ad-hoc signed for local integrity checks and remains unsandboxed; neither it nor the separate ad-hoc sandboxed build is Developer ID-signed, notarized, or App Store-ready. Selected-folder traversal works in the tested sandbox flow, while sandboxed duplicate reads, history placement across relaunches, stale-bookmark recovery, and protected-folder failure states remain to be validated. macOS may deny access because of file permissions, ACLs, system protections, or data-protection rules. Disker must surface those cases as incomplete coverage. It must not claim whole-volume visibility or attempt to grant itself Full Disk Access. See Apple's [App Sandbox](https://developer.apple.com/documentation/security/app-sandbox), [accessing files from the macOS App Sandbox](https://developer.apple.com/documentation/security/accessing-files-from-the-macos-app-sandbox), and [NSOpenPanel](https://developer.apple.com/documentation/appkit/nsopenpanel) documentation.
